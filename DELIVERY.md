# MasarX: delivery

The Delivery Lead owns this file.

Follows engineering standard v1.29.3.

## Branching and merging

- The `main` queue permits one concurrent build. Use it without admission caps, drains or bypasses. Keep one migration item and one non-migration item in progress at a time.
- The manual merge hold is retired. The DEV apply guard (G1–G3) protects DEV database applies.
- The thread that made the change pushes its topic branch and opens its own PR ready under the project's agent identity. Each PR names its issue (`Closes #n` or `Refs #n`).
- Use the approved tree-publisher App helper for authenticated GitHub work. If the helper fails, stop and report it to Delivery. Keep installation tokens and signing material out of output and shared artifacts. The owner login is reserved for approved settings changes and release tags.
- Never force-push, rewrite public history or push directly to `main`. Change repository or organization settings only through an approved packet naming the exact setting and target value. Record the before and after values.
- For a non-critical change, the thread that made it enables auto-merge as soon as it opens the PR. Use `enablePullRequestAutoMerge` with `SQUASH` and set `expectedHeadOid` to the PR head. GitHub merges it on green required CI.
- For a [critical change](AGENTS.md#critical-changes-the-only-changes-that-get-a-review), get one independent review of the full diff in parallel with CI. The deciding reviewer posts a PR comment with `VERDICT: GO <40-char sha>` or `VERDICT: NO_GO <40-char sha>` on line 1 and `Reviewer: <model>, effort <level>` on line 2, followed by a public-safe summary of findings.
- Reassess the classification before each push. Disable auto-merge or remove the PR from the merge queue before pushing again. If a non-critical PR becomes critical, follow the critical-change process. For a PR that remains non-critical, re-enable auto-merge with the new `expectedHeadOid` after the push. A push after a GO that leaves every listed critical file as reviewed needs no new verdict, subject to the manual admission check below. A push that changes a listed critical file, and any fix after a NO_GO, gets a re-check of that push only by the same reviewer, ending in a new verdict.
- Until the [CI verdict step](https://github.com/MasarX/masarx-platform/issues/655) is live, open critical PRs with auto-merge off. The merging thread waits for a GO naming the current head before enabling squash auto-merge with that `expectedHeadOid` or entering the merge queue. When a push leaves the reviewed critical files unchanged, the reviewer posts a GO naming the current head for manual admission without repeating the review. PRs that edit `.github/workflows/**` keep this manual check after the CI step is live, until the reviewer App's `review-verdict` status is required by the ruleset.
- Changes to `main` merge only through the merge queue, using `SQUASH`. The required checks are `ci-gate` and CodeQL code scanning. CodeQL alerts of high severity or above block merging. The Delivery Lead owns the merge queue, CI health and speed, releases, deploys, rollback and alerts.
- At push time, assign a fresh migration timestamp block above the newest migration on `main` and keep its files in landing order. For a rename-only re-stamp, compare the pre-stamp and re-stamped commits. Verify every migration is `R100` in `git diff -M --name-status` and has zero content lines in `git diff -M --numstat`. The append-only and ordering gate is in [migrations.cjs](scripts/ci-hosted/migrations.cjs).

- Measure product speed in a browser on production-class hardware against a written usable state. Before tuning a slow action, capture its request waterfall and client and server timings.
- Before replacing a CI tool, compare both tools on the same inputs and record any lost coverage. If a change leaves `main` or the queue red for 30 minutes, revert it through the protected PR path. Track flaky tests as high-priority bugs and fix or revert the cause.

## Test policy

- Test each changed behavior with a regression that fails before the fix. Use unit tests for logic, integration tests for affected database, queue and API boundaries, and end-to-end tests for core user jobs. Freeze clocks and wait for observable state. Preserve product guards when fixing tests. Trunk test edits need a recorded Master exception. A replacement preserves the existing assertions or identifies the design decision that retired them. Removal also requires two weeks of evidence that the test only detects change. Keep authorization, privacy, migration and concurrency tests.
- Add property and edge-case tests for code that accepts untrusted or varied input. Exercise parsers, limits, boundaries, time zones and daylight saving transitions where they apply.
- For every bug that reached `main`, add its failing case as a regression test or a row in the project's golden cases.
- Fix failures at their source. New failures block landing. Never rerun an unchanged failure or use retries, skips or longer timeouts to turn a failing check green. The existing exceptions are listed under [Deviations](#deviations).
- Use local services and mocks for routine tests. The cloud qualification checks are listed under [Deviations](#deviations).
- Hosted Jest ([jest.cjs](scripts/ci-hosted/jest.cjs)) reads the target-base known-failure baseline at `config/ci/known-failures.txt`. A missing baseline is empty. The file is absent on `main`. A candidate can retain or remove target-base entries.
- Only `npm run verify:cloud:e2e-gate` reads the [UI flake quarantine](config/ci/ui-flake-quarantine.json) for its cloud E2E summary outside hosted CI. Each entry carries an owner and expiry (`burn_down_by`).
- [database-result.cjs](scripts/ci-hosted/database-result.cjs) requires all six pgTAP shards and an exact count and name match against the SQL test inventory. [database-selfcheck.cjs](scripts/ci-hosted/database-selfcheck.cjs) probes missing and incorrect coverage.
- The digest-pinned Docker guard enables and verifies `docker-init` for the from-zero database build and pgTAP shards on GitHub-hosted runners.

### Nightly full suite

The **Servers nightly host** runs [nightly-full.sh](scripts/ci/nightly-full.sh) at **00:30 UTC** daily. The service serializes manual and scheduled starts and caps each run at four hours. It checks out public `main` anonymously, verifies the tested commit against public `main` at startup, and removes the checkout after copying the test result and log. The nightly never gates merges.

Use the Node version in `.nvmrc`, the Supabase CLI and a dedicated rootless Docker daemon for disposable local PostgreSQL, Auth, REST, Storage and Edge services. The command starts with an allowlisted environment and job-local home and caches. It requires free fixture ports, disables Studio, and verifies that Supabase publishes fixture ports on IPv4 loopback. The first server run records listener addresses and cleanup. The command runs the existing Jest, Vitest, pgTAP and Playwright suites. [Nightly exclusions](config/ci/nightly-out-of-scope.json) record the reason and alternate coverage for each omitted suite. Unexplained skips fail the run.

Servers delivers each run's private `result.json` and `nightly.log` under its UTC date. Delivery runs [nightly-report.cjs](scripts/ci/nightly-report.cjs) with the delivered results directory through the issue-scoped App. Set `GITHUB_REPOSITORY` and `NIGHTLY_DENY_CHECK` for the repository and privacy check. If needed, set `NIGHTLY_DENY_BASH` to the shell that runs the checker. The reporter verifies the run's commit against current public `main` and screens the exact text before publishing. It files a same-day Bug for a red or error result or a result missing at 06:00 UTC. Recurrences with the same failing suites go on the open Bug, once per result. Public reports carry the UTC evidence date, publishable test names and screened failure markers. Use `--dry-run` to inspect the proposed reports.

## Environments

- `ci` runs per change and creates an isolated database with generated fixtures when the database lane runs.
- `dev` hosts the integration database and receives deployments on merges to `main`. Use generated fixtures for validation.
- `stg` is the GitHub environment for production-like qualification with approved test data. The deploy gate is pending.
- `prod` is configured for production data and approved releases. Production deployments are paused.
- Keep each environment's data separate. Use generated fixtures for tests.

### DEV Management API credentials

Use fine-grained tokens scoped to the single DEV project. The DEV environment secret `SUPABASE_DIAGNOSTICS_ACCESS_TOKEN` serves the API schema and Edge log diagnostics with Data API Config Read (`data_api_config_read`) and Logs Read (`analytics_logs_read`) only.

`SUPABASE_ACCESS_TOKEN` is shared by [Deploy DEV](.github/workflows/deploy.yml), the [DEV outbound probe](.github/workflows/dev-outbound-probe.yml), and the [signed-in DEV sweep](.github/workflows/dev-sweep-users.yml). The shared credential needs Project Settings Read, API Keys Read, API Key Secrets Read, Connection Pooling Read, Edge Functions Read-write, Edge Function Secrets Read-write, Auth Config Read, and Database Read-write. The Delivery Lead rotates it before expiry, with a maximum validity of 90 days, and verifies the sweep and a subsequent DEV deploy before retiring the previous credential.

### Signed-in DEV sweep

Dispatch [DEV design sweep users](.github/workflows/dev-sweep-users.yml) from `main` with `environment=dev`. Each successful dispatch refreshes the passwords for all three accounts. Use the successful run ID before the encrypted artifact expires after one day.

Run `node scripts/dev/fetch-sweep-credentials.mjs --run <id> --key <path> --out <path>` with an authorized GitHub CLI and OpenSSL on `PATH`. Set `GH_CLI` to the GitHub CLI executable if needed. Choose a new output file outside Git worktrees, feed it directly to the sweep runner and remove it after the sweep. Keep credential entry and the file out of logs, captures and issues.

The sweep covers the deployed Console and Portal from the `console` and `portal` jobs in [Deploy DEV](.github/workflows/deploy.yml). Sign in with the normal email and password forms. Start at the Console dashboard with `finance_viewer` and Portal Shipments with `sender_user`.

Use the synthetic tenant's read-only `dispatcher` account for Console `/operations/pickups/waves`, `/operations/pickups/requests`, `/operations/routes` and `/resources/warehouse_transfers/new`. The pickup ledgers and route workspace can be reviewed in read-only mode. The transfer manifest form renders with its lookup inputs disabled. Sweep the available states without submitting forms. The [role configuration](config/dev/sweep-roles.json) lists the allowed permissions.

## Releases

- The [tag workflow](.github/workflows/release-on-tag.yml) checks annotation, tag syntax, first-parent history on `main` and qualifying exact-SHA `ci-gate` evidence before building and attesting the static Landing archive. A release-candidate tag retains the archive and checksums as a workflow artifact for staging qualification. A version tag publishes them to the GitHub Release with static artifact notes. The Delivery Lead updates those notes from the milestone's closed issues and then closes the milestone.
- GitHub's active `release-tags-create` and `release-tags-immutable` rulesets restrict tag creation and protect `v*` tags from updates and deletion.
- Release tags (`vX.Y.Z` and `vX.Y.Z-rc.N`) are annotated and are created with the owner's login, the organization admin that `release-tags-create` allows, as the engineering standard permits for tag creation. The App never creates release tags.
- Before creating a tag, fetch `origin/main` and set `RELEASE_SHA` to the full target commit SHA. Run `git merge-base --is-ancestor "$RELEASE_SHA" origin/main` and `git cat-file -e "$RELEASE_SHA:.github/workflows/release-on-tag.yml"`. Stop if either command fails. Verify against GitHub that the commit is in the first-parent history of `main` and that a `ci-gate` check run succeeded on that exact SHA. After creating the tag, read back the tag ref, the annotated tag object's name and the commit the tag object points to.
- For a hotfix, cut from the deployed tag, test the fix, get the owner's explicit approval before a production deploy, and merge the deployed fix forward through the protected PR path.

## Deploys

Hosted lint builds affected Edge Functions with the pinned Deno toolchain and root lock, resolves the resulting bundles offline, and verifies their checksums. DEV applies the same build checks before database writes and verifies that every function on the deploy list has a valid bundle checksum immediately before upload. Use the same builder and checksum check for the production release artifact.

Renderer jobs queued during the database-to-Edge rollout keep their request IDs. The database releases an older HTTP worker's lease before dispatch. If an upgraded worker reaches the v0.1.0 renderer during an interrupted upload or rollback, the worker recognizes the pre-dispatch role rejection and asks the database to defer the job until its lease deadline. Once both Edge functions are compatible, the worker resumes each queued render or print with a fresh lease.

The v0.2.0 production deploy plan uses the same renderer signing key derivation as DEV, HMAC-SHA256 of the production project JWT secret with the versioned `masarx-renderer-sign-v1` label. The operator runs the derivation on the operator machine and installs the key in the production Edge secret store. Production signing material stays on the server and never enters GitHub.

- DEV deploys run from `main` only. The database job serializes applies in one concurrency group with cancellation disabled. Its configuration guard checks whether deployment is configured. The database merge gate is hosted from-zero replay plus pgTAP. Verify the DEV apply after every migration merge and retain the merged SHA, deploy result and applied migration evidence.
- The Console and Portal jobs publish preview builds and assign them to their verified DEV domains from the DEV origin allowlist. A job skips alias assignment if a newer commit is already deployed to that address. A new alias or a deployment without commit metadata can be assigned only by a run at the main tip. After assignment, the job gives the address up to 120 seconds to serve the exact marker over HTTPS without provider sign-in. It logs the HTTP status on each attempt and fails if the marker never appears. Use the stable addresses for the [signed-in DEV sweep](#signed-in-dev-sweep).
- The [manual DEV outbound probe](.github/workflows/dev-outbound-probe.yml) shares the database apply concurrency group. It runs 20–50 synthetic jobs through inline dispatch and one through the scheduled outbound worker, reports aggregate create-to-completion timings, and requires a leased Edge completion for the worker job. The synthetic fixture and jobs tagged `dev-outbound-probe` remain in DEV for audit.
- The M6 DEV apply guards are active in [apply-guard.cjs](scripts/deploy/apply-guard.cjs) and the deploy workflow.
  - G1: Skip a superseded push when a newer deploy run targets the current tip of `main`. Refuse the apply if the replacing run ended without success or failure.
  - G2: Stop applies if the latest attempt in the 30-day history was unsuccessful, until `DEV_DB_REARMED_AT` is set to a valid timestamp later than that attempt's completion and no later than the current time. Treat a completed database job with missing step records as a possible apply attempt.
  - G3: Before a manual apply, require `expected_sha`, the run SHA and the current `main` tip to match.
  - G4: Once apply starts, write a sanitized apply summary on exit, including failure, and remove the temporary environment file and raw apply log.
- The [database retry helper](scripts/deploy/supabase-db-push.sh) inspects the failed migration before retrying a lock error. It refuses replay when it cannot identify the failing migration and statement, finds a statement whose effects can survive rollback, finds a commit before the final statement, or sees the migration history write fail. Review the migration history and any committed effects before rearming a failed apply.
- Review each deploy gate once and record its GO. The Portfolio Lead gives the GO for non-production deploy gates. Once approved, the gate releases each passing change automatically and writes an audit row. A new kind of change needs a new GO.
- The routine DEV deploy audit row is the workflow run summary. It includes the G1–G3 guard decisions, the G4 apply summary and the final job's per-surface results table.
- Each production deploy requires the owner's explicit approval. Production deployments are paused until the production deploy gate is ready. Verify a production backup before every production deploy. Keep the previous version ready, check health after deploy and roll back immediately on failure.
- Use the [production release runbook](docs/ops/production-release.md) for the managed database setup, backup check, approval preflight and artifact promotion.
- Gap: No production rollback command or staging/production deploy audit row is defined.

## Security

- The Delivery Lead acts on Dependabot, code scanning and secret scanning alerts from both default and generic patterns. Record new high or critical findings the same day. Report vulnerabilities through the repository's private reporting channel. [dependabot.yml](.github/dependabot.yml) configures weekly grouped npm and Actions updates.
- Follow the [privacy screening rules](AGENTS.md#privacy) before pushing or posting public text.
- Treat a privacy hit on pushed material as an exposure. Revoke and rotate exposed credentials immediately through the authorized owner. Escalate exposed personal data, customer data, hosts or internal names to the owner as a private blocker and propose a remedy. Leave any history rewrite or cache purge to the authorized incident response.
